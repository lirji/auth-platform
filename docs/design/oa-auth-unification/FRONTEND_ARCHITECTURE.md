# P5 前端架构与验收范围

本设计落实已批准P5，复用auth-console React18/Router6/Ant Design5/React Query和现有OIDC PKCE；不改公开免登录project-portal，不引入BFF进程、微前端或第二组件体系。P6及生产不在范围。

## 决策与边界

用户确认Q-EXT为真实commerce门店/商家协作：受邀成员仅访问指定门店商品，申请限时导出。它不是供应商订单模型。内部试点沿用commerce真实门店/商品与受控写路径；后端逐次执行范围检查。OA只拥有审批/待办，日常工作台不以OA可用为前提。

P5-01先补齐本人组织与已关联应用目录的后端只读契约；其余写入口沿用P1—P4，必要展示缺口在所属切片先冻结契约再实现。组织由本人有效Membership产生，应用卡片由后端关系/准入/当前权限过滤。管理员能管理不等于能进入业务。

## 路由、状态与模块

`/governance`为统一工作台，子路由apps、roles、grants、requests、invitations、permissions、audit；通过URL的tenant/application/environment指定上下文，每个标签页独立。现有`/w/:workspaceId`运维工作区保持。认证后请求携带当前Access Token，服务端重新解析成员；query key包含主体/成员代际/租户/应用/环境。切换组织或应用取消旧查询并卸载上下文子树，清理列表游标、详情及草稿，迟到响应不得覆盖新上下文。组织数据不得从localStorage建立权威。

本人申请、通知、权限仅本人当前代际；角色/授予/策略/邀请/诊断/审计使用服务端管理边界。202显示受理或待生效，APPROVED不能转换ACTIVE；401重新登录，403明确无权，409保留命令并刷新冲突对象，5xx显示可重试服务错误并清旧允许结果。写入一次生成command_id，未知结果重试复用原命令，不自动换键重提。

## 视觉与交互覆盖

方向假设：沿用现有theme/colors与PageHeader，浅背景、白作业面、现有主色/36px控件/14px正文；没有声称用户审过新稿。工作台以组织选择与当前应用任务为主，无伪造统计和装饰图。桌面1440及窄屏390验收，中文系统字体，长ID折行/复制，宽表横向滚动。

| 切片/入口 | 主任务和关联交互 | 容器与验收 |
|---|---|---|
| P5-01 apps | 组织选择、应用导航、分页、管理入口 | 顶部上下文+卡片；多组织/多标签页、空/加载/错误，入口无Token并源自已登记路由 |
| P5-02 roles/grants | 固定角色差异、授予成员、投影查询 | 列表+有界表单弹层；版本/能力差异和影响数量，提交校验与202，不填原始JSON |
| P5-03 requests/invitations | 策略选择、提交、详情、取消、通知、邀请接受；OA办理依据 | 路由详情保留上下文，短提交弹窗；成员类型限制、固定范围/期限、审批和执行分别展示 |
| P5-04 permissions/audit | 同Grant来源/范围解释、撤权回执和剩余来源、管理审计 | 分组详情与列表；不可把REVOKED数据库状态冒充全局完成；越权拒绝 |
| P5-05/06 commerce | 内部受控业务操作和外部门店商品/导出 | 复用原业务前端；真实数据库、授权/撤销/下载复查，前后端反例一致 |
| P5-07 | 登录回调、过期会话、刷新深链、服务错误、窄屏 | 真浏览器截图并实际查看；列表→表单/详情→提交反馈→返回，焦点/Esc/关闭和未保存保护 |

各页使用AntD语义组件，主次按钮清晰，不新增自制Dialog/Button。详情按身份、能力范围、生命周期、执行结果分组，普通用户不看原始协议JSON。列表游标不虚构总数。视觉截图和行为证据分开记录；缺必需证据不能DONE。

## 未决及后续

Q-EXT已由本轮用户明确选定；P5-01无业务输入阻塞。后续管理/解释/邀请缺口按本阶段授权有界补齐，未完成前不谎称已有接口。实测证据写phase-5，不用页面完成率替代真实业务验收。


## GUX 2026-09 权限控制台体验改版（已实现，本地可验收）

本节是 `/governance` 及其直属页面的新视觉/交互方向，实施后替代上文 P5 的默认 Card 配方；P1—P7 业务契约与安全边界不变。实现以源码为准；用户已明确批准“设计并实现，可在本地浏览器验收”，当前本地5273静态前端已更新，未部署生产。用户要求按前端 Skill 重新规划，以 Awwwards、Webby、FWA 的优秀体验为质量目标。用户已确认的安装级偏好是企业工作台简洁精致、重层级/排版/留白/清楚操作；本节具体视觉选择为设计假设，未冒充用户审稿认可。

### 1. 范围、事实与目标

- 范围：`/governance` 首页、共享组织/应用壳层，及 access、permissions、requests、policies、invitations、audit、diagnostic 的关联交互。邀请接受页仅验证入口兼容，不重做登录页、`/w/:workspaceId` 运维工作区或商城。
- 当前源码：`auth-console/src/features/governance/shell/GovernancePage.tsx`、`router/routes.tsx`、`api/governance.ts`、`governance/context.ts`，以及各 Governance 子页面。
- 改版前浏览器观察：真实组织 `local-commerce`、应用 `commerce`、环境 `local`；内部成员；有管理入口，当前没有可用业务入口。现有组织卡片占用大量空间，应用卡片内有六个等重动作；首页没有持久作业导航。这是实际观察，不是待办/角色/权限数量的依据。
- 用户提供的 URL 含 `amp;application`/`amp;environment` 转义残留与正常同名参数；导航须生成规范参数，不扩散错误参数。合法 `application`/`environment` 优先；只清理已识别残留，不接受任意参数别名作为安全上下文。
- Brownfield：React 18、Router 6、TypeScript、Ant Design 5、React Query 5、Vite 5、OIDC PKCE 已存在。具体已安装版本以 lockfile 为准；不升级依赖、不引入第二组件库、微前端或 BFF。
- 主作业：成员查本人权限/申请；管理者查看固定角色、授予、策略、邀请与审计。成员身份不等于管理能力，管理能力也不等于业务访问权。
- 成功目标：用户在首页能清楚识别组织、应用、环境、业务入口是否可用及可做的下一步；子页之间可直接切换；单来源授权的能力、范围和期限不被视觉合并。
- 非目标：虚构安全评分、全局权限总数、审批待办数、授权趋势、AI建议、组织关系图、批量操作、全局搜索、导出和暗色模式。

### 3. 信息架构与应用形态

仍是一个 auth-console 应用。保留现有路由与 API，统一壳层由 `GovernancePage` 管理；设计不改变工作区权限。

```text
/governance                    我的工作台 / 当前组织的应用与可执行任务
  /permissions                 我的权限来源 → 单来源详情弹层
  /requests                    我的申请与通知 → 既有详情/执行状态 → 申请表单
  /access                      授权管理 → 固定角色/授予 → 新版本/授予弹层
  /policies                    申请策略 → 策略详情/创建弹层
  /invitations                 外部邀请 → 创建弹层/撤销确认
  /audit                       授权审计（只读）
  /diagnostic?grant=…           授权来源诊断与回收（来源深链）
/invitations/accept             接受邀请（既有独立入口）
```

桌面侧栏宽 224px，分为“工作台”“个人访问”“授权管理”；管理分组由当前应用 `management` 事实决定是否展示，直接访问仍由服务器判断。普通成员只看到少量作业时使用紧凑导航区，不留下空管理组。未选择应用时，个人/管理子入口解释“先选择应用”，不默认选中不在当前目录中的应用。

应用目录没有服务端全量搜索；保留游标翻页。首页多应用以紧凑列表选择，右侧显示选中应用的真实入口与状态；只有一个应用时直接展示应用任务面，避免空列表占位。翻页与选择保持显式 URL 语义，不把当前页条数标为总量。

### 4. 页面构图与组件体系

- 顶部 64px 上下文条：组织选择 → 当前应用 → 环境；右侧“接受邀请”和身份菜单。退出登录放身份菜单，保留明确文字。
- 主工作区页边距 32px（窄桌面 24px），阅读面最大 1240px；表格可以使用全工作区宽度。页头一个 H1（28px/600），小型功能标签与一句说明，刷新为轻量次操作。
- 首页为真实应用任务面：应用标识 `commerce`、环境与业务访问状态；状态说明及可用业务入口位于主内容区。`management=true` 显示独立“管理授权可用”事实，并以“进入授权管理”为当前管理员的主动作；不存在业务入口时不能显示可点击的“进入商城”。
- “管理授权可用”和“业务访问未开放/暂时无法确认”并排但语义独立，禁止画成“管理员必然通往业务”的权限链。状态来源均为同一个当前应用响应。
- 个人任务区使用两条精炼任务行（权限来源、申请与通知），不是重复侧栏的六宫格卡片墙；各行含清楚目的、单一文字入口。策略/邀请/审计作为侧栏的持续作业，不再堆进首页按钮排。
- 子页先任务页头，再结果/筛选，再列表与游标；表格不再套多层白色 Card。只读说明由大面积 Alert 收敛为有图标的说明行，真正失败保留醒目 Alert。
- 始终复用 AntD Menu/Select/Button/Table/Form/Drawer/Modal；自定义领域布局不重复造交互原语。
- 静态设计稿见 [桌面稿](governance-experience/overview.svg) 与 [窄屏稿](governance-experience/narrow.svg)：只展示已观察的首页事实与导航结构，不代表可运行 UI、API 验证或用户确认。

表格列宽：角色 180–220px、状态 140–180px、时间 168px、操作 112–144px，能力为剩余弹性列；长状态用短标签与相邻说明，不能用巨大标签撑爆列。宽表局部横滚、无整页横滚。无支持的 API 不添加全量搜索、筛选、总页数或批量复选框。

### 7. 状态、URL 与数据流

沿用 `contextKey(subject, membership, generation, partition)`；query cache 的身份/组织/应用/环境隔离不变。URL 保存 tenant/application/environment、原有各列表 cursor、grant/request 详情选择；表单草稿留组件内。布局偏好不能成为业务授权权威。

- 切换组织：取消旧查询，清应用和列表/详情参数，卸载上下文子树；切换应用同样清理无关 cursor/详情，保留 tenant。不能让旧应用 `after` 导致新应用不可达。
- 深链：仍先验证本人组织及当前目录；目录是游标页，不能凭“当前页没有 app”改成全局不存在。当前契约缺精确应用查找端点，先保留现有边界并给“返回应用目录”恢复路径，不偷偷新造 API。
- 错误后禁用/移除旧业务入口和旧允许结果，禁止 stale-allow。刷新期间可保留布局，但旧事实不能作为新权限依据。
- `management` 只控制导航可见性，所有命令依然经既有服务端授权。管理页不能作为首页快捷自动写入。
- 新布局最多复用现有本人组织/应用查询，不增加全应用 N+1 权限/审计查询。首页不展示缺少聚合 API 的统计/待办。

| 状态 | 页面表现 | 恢复方式 |
|---|---|---|
| 首次 loading | 固定布局骨架与加载标签，不闪空态 | 读取现有查询 |
| 组织/应用 empty | 点明当前无有效组织/关联应用 | 切换有效组织、接受邀请等真实入口 |
| NO_ACCESS | 业务入口未开放，管理能力另行展示 | 查看本人权限/申请；不冒充故障 |
| UNAVAILABLE / 5xx | 无法确认权限/服务暂不可用，旧允许结果失效 | 原上下文重试，不显示绿勾 |
| 401 / 403 | 会话失效 / 无权操作 | 现有登录返回或返回工作台 |
| 202 / PENDING | 已受理、等待生效，保留实际回执 | 只刷新/查询既有命令 |
| 409 | 冲突对象与当前版本提示，保留输入 | 读最新事实后确认；不换 command_id 重试未知命令 |
| 校验错误 | 字段级提示，聚焦首个无效字段 | 保留其余输入 |
| 已完成 | 使用契约已确认结果，更新相关列表 | 可继续处理下一项 |
| 未找到详情 | 说明当前页/上下文未找到 | 回列表，不臆造全局 404 |

### 8. 工程落地与有界切片

拟新增布局/展示组件放 `auth-console/src/governance/`：`GovernanceShell`、`ApplicationWorkspace`、`GovernanceNavigation`。保留 `GovernanceContext` 与客户端调用；若提取 context 类型，以消除循环依赖为限，不重写业务层。

新增样式 `styles/governance.css`，由 `.governance-shell` 根节点隔离；主题值引用唯一 token。保持公共 PageHeader 的其他消费者原样，治理页标题在范围内统一。现有表单命令继续使用原 `useCommand`；详情分组复用领域组件。保持 AntD 可访问原语，CSS 不侵入无关登录/运维路由。

实施顺序（需要明确实现范围后进入 implementation-slicing；本表不宣称已获实施批准）：

1. GUX-01：规范 URL、上下文条、按权限的稳定导航和真实首页任务面。代表路径：工作台 → 我的权限 → 返回。
2. GUX-02：授权管理/单来源详情/诊断，角色与授予分区、弹层分组和按钮层级；验证原命令保护。

### 9. 质量门槛与迭代办法

设计以奖项级作品为参考，但不存在自评保证获奖的事实。采用缺陷闭环，不写“自评 9.8 分=获奖”：每轮记录具体观察、修正、截图和操作证据。

- 设计检查：布局/操作层级和真实数据支持逐项追溯，覆盖所有本范围关联界面。
- 首次实现检查：1440×900、1280×800，首页与列表/打开详情/打开编辑分别截屏并实际查看；无重叠/裁切/异常空白，主操作一眼可辨。
- 窄屏回归：390×844、桌面 200% 缩放；侧栏变为可关闭弹层，顶栏上下文可换行，正文单列，宽表只局部滚动。沿用既有 390 宽度范围，不新增移动产品。
- 交互检查：实际键盘完成组织/应用选择与路由导航，跳过导航链接、清晰焦点、Esc、焦点返回、浏览器后退、原筛选/游标恢复；减少动态偏好无强制动画。
- 状态检查：无权、空、网络错误不混淆；pending/202/unknown 不当完成；长 code/ID 可完整读取；草稿切换/关闭保护有效。
- 安全回归：身份/分区缓存隔离、管理入口与业务入口独立、未知结果重试原命令；不为了截图授予生产权限或修改既有业务数据。
- 性能目标：不增加字体/图片外部请求，不引入动效运行库，不新增首页 N+1 请求；性能数字以实测为准，不预写达标。
- 每轮修复后重新查看受影响界面，至少完成“整体层级”“真实任务细节”“窄屏与错误路径”三类检查；只有必需检查全部通过才标实现完成。主观奖项质量仍由实际用户/评审判断。

当前状态：GUX-01—03 已实现，实际 Chrome 桌面1440、窄屏390、200%缩放与代表交互已复核，构建和6项上下文测试通过。验证范围、修正轮次与未验证项见 [TEST_RESULT](governance-experience/TEST_RESULT.md)。浏览器扩展 request-header-policy 失败时采用原生 Chrome UI 验证，未声称扩展已恢复。外部奖项评价、完整辅助技术测试与性能指标仍未验证。
