# 菜单、角色与授权变更治理讨论

记录日期：2026-10-02。

状态：讨论归档／后续建设建议。保存本文件不代表批准实施，不改变已有契约、实施切片或运行配置。以下明确区分源码已实现行为与建议目标；未进行生产环境验证。

## 1. 背景与目标

本次讨论源自电商实际菜单接入权限平台后的问题：集中设置角色权限有什么价值，关联项目菜单发生变化时怎样同步，API 接入能否用于生产，以及如何处理人员变化、撤权、故障和回退。

集中管理的核心价值是统一回答：谁，在什么组织和环境下，可以对哪些数据执行什么操作，权限来自哪里，何时失效。菜单是入口展示，角色组织业务能力，授权将角色赋予具体成员并限定范围和期限。

## 2. 能解决的现实问题

| 问题 | 治理目标 | 必要条件 |
|---|---|---|
| 各项目分别配置权限，入职、调岗需重复操作 | 按岗位集中分配和检查权限 | 项目接入统一身份与服务端授权；人员变化链路需对接 |
| 同名角色含义不同 | 展示角色包含的实际业务能力和版本 | 权限编码有稳定、明确的业务语义 |
| 不知道某人为什么有权限 | 展示授权来源、角色版本、数据范围、有效期 | 查询全部有效授权来源，不能只看一个角色 |
| 临时授权和离职权限遗漏 | 到期失效，人员状态变化后核对访问资格 | 明确人员、成员关系、组关系和授权的生命周期 |
| 管理员误授高权限 | 限制可授予上限，保留变更审计 | 服务端检查委派边界；审批按业务风险设计 |
| 系统升级悄悄扩大权限 | 发布前发现能力和授权影响 | 变更预览、语义评审及显式角色迁移 |

示例：订单客服具有订单查询能力，授权范围是所属门店，有明确有效期，不具有退款能力。不能仅凭“客服”这个名称推断操作或数据范围；范围必须由服务端落实。

## 3. 模型与职责边界

| 对象 | 职责 | 边界 |
|---|---|---|
| 菜单 | 中文名称、层级、顺序、页面地址及可见性关联 | 显示入口不等于允许所有页面操作 |
| 权限能力 | 稳定编码代表某个业务操作，关联资源类型 | 不用菜单名称或路由充当权限身份；含义扩大需评估新编码 |
| 角色版本 | 固定的一组业务能力 | 新版本不隐式改写旧版本授权 |
| 实际授权 | 成员、角色版本、组织／环境、数据范围、有效期、来源 | 多个有效来源可能共同构成最终权限 |
| 业务项目 | 页面、路由、接口及业务数据 | 发布目录不能生成业务页面；接口独立执行权限与数据范围校验 |
| 权限平台 | 目录、角色、授权、审计与决策 | 不直接写其他项目的业务表，不成为业务数据的第二写入入口 |

当前个人菜单的 `any_of` 表示任一关联能力获准即可展示该入口，并不授予页面内所有能力。隐藏菜单不能阻止直接访问接口，服务端必须验证每次请求：[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)。

## 4. 当前实现事实

核对基线：Auth `95c3ffac5a8c73daa99da3fc8aeaf8b643e63b8a`。电商导航观察基线为 `aeed09efb291e9120e2ad05d14280caee18e7905` 的 `frontend/src/iam/CentralShell.tsx`；此处记录固定版本事实，不代表以后电商版本仍相同。

| 项目 | 已实现行为／当前限制 |
|---|---|
| 目录接入 | 从真实导航与权限映射生成清单，由应用 Owner 调用预览／发布 API；不是常驻自动同步 |
| 发布 | 权限快照和菜单展示快照同事务保存，版本不可原位改写；同版重试需保持内容一致 |
| 能力兼容 | 新版必须保留原能力编码及其资源类型、风险级别，可以新增能力；没有完整的能力退役生命周期 |
| 菜单变更 | 新版可调整／移除菜单；删除菜单不会删除角色、授权或原能力 |
| 新增能力 | 目录发布本身不创建角色、授权或扩大管理员委派上限 |
| 角色 | 按租户／应用／环境管理固定版本，已有 Grant 绑定具体角色版本；新增版本不自动迁移旧授权 |
| 停用与故障 | 有受审计的紧急能力停用；中央决策在依赖不可用／投影未就绪时拒绝放行，不承诺未经测量的零延迟撤权 |
| 当前预览 | 主要返回新增／保留能力和版本、摘要；未提供完整菜单差异、受影响角色及人员统计 |
| 环境隔离 | 角色与授权有环境维度，应用菜单目录目前按应用管理，没有环境维度 |
| 发布身份 | 当前受控发布使用已登记的真实 HUMAN Owner；不能将其描述成已经具备通用机器发布身份 |
| 电商侧栏 | 观察基线使用 `centralGroups` 生成侧栏和搜索；权限平台目录发布不会重写其导航或路由，侧栏尚未按平台个人菜单结果过滤 |

## 5. 菜单与权限变化的处理建议

以下是目标处理规则；未实现的部分不能依靠当前发布 API 自动完成。

| 变更 | 建议处理 | 授权影响 |
|---|---|---|
| 名称、图标、排序调整 | 更新展示版本；图标支持按后续契约决定 | 通常不改变能力，但仍检查菜单绑定未变 |
| 地址改变 | 校验路由存在、来源合法、权限绑定正确；与项目版本配套发布 | 不以地址变化代替重新授权 |
| 新菜单复用已有权限 | 展示哪些已有持权人会看到入口，检查是否扩大业务语义 | 原持权人可能直接看到新页面，不能一概视为无影响 |
| 新菜单增加新能力 | 登记目录，默认不授予普通用户，由有权管理员明确配置 | 发布不是授权；不得自动加入已有角色 |
| 删除菜单 | 移除入口，检查能力是否仍被其他页面／接口引用 | 菜单消失不代表接口权限撤销 |
| 原能力含义扩大 | 评估使用新权限编码，安排兼容与迁移 | 防止旧角色未经决定获得更大操作／数据范围 |
| 更改能力编码 | 保留兼容窗口，迁移角色与接口后再退役 | 当前发布规则要求旧能力保留，直接删除会冲突 |
| 角色增加／减少能力 | 创建新版本，预览具体授权迁移对象并显式迁移 | 旧 Grant 继续绑定旧版本；减少新版能力也不会自动撤掉旧版 |
| 紧急禁止某项操作 | 使用独立停用机制，核验实际决策与恢复记录 | 不等待普通菜单发布，不能以隐藏入口作为撤权 |

特别注意：“查看订单”从所属门店扩大为全部门店，即使权限编码未变，业务范围也已扩大。接口和范围实现的变更需要评审，不能仅凭清单摘要一致认定安全。

## 6. API 接入与生产发布建议

API 是跨项目发布契约的合理方式，生产可继续采用；需要补齐受控发布链路，不能把本地人工脚本直接当作完整生产流程。

| 方式 | 适用性与取舍 |
|---|---|
| 人工脚本调用 API | 适合初始化和有界维护；容易忘记同步，需要记录和核对 |
| 源码清单＋CI/CD 调用 API | 推荐方向：随项目版本生成、检查、预览、审查和发布，便于追溯 |
| 管理页面上传清单 | 可作为受控补充，仍需同样的校验、身份和审计 |
| SDK 在应用启动时自动注册 | 不作为默认生产方案；多实例和滚动升级可能竞争发布或恢复旧声明 |
| 直接读写关联项目数据库 | 增加所有权和结构耦合，不作为菜单发布首选 |

建议由一份源码声明生成项目导航和发布清单，覆盖稳定菜单标识、名称、父级、路由、关联能力；权限声明另记录业务含义、资源类型及风险。业务页面仍由项目实现，平台按授权结果提供导航提示。

建议链路：

```mermaid
flowchart LR
    A[项目菜单与权限声明] --> B[CI 校验与变更预览]
    B --> C[查看受影响角色和人员]
    C --> D[发布目录版本]
    D --> E[按需迁移角色与授权]
    E --> F[核对生效结果与审计]
```

生产落地前还需明确：

1. 发布身份：建立受限机器发布身份及显式委派契约，凭据放在受控机制内，不放前端或仓库；当前 HUMAN Owner 模型需要正式扩展。
2. 环境：选择独立实例／数据库隔离，或扩展目录环境维度；避免测试目录覆盖生产目录。二者尚未在本讨论中定案。
3. 配套版本：记录项目提交、清单摘要、目标环境和平台目录版本；检查当前运行路由与已发布清单是否一致。
4. 发布兼容：旧／新项目版本共存时，校验入口、能力与接口绑定兼容；发布顺序根据实际变更决定。
5. 权限治理：展示信息变更可按规则自动发布；语义变化、角色迁移、风险操作需要明确处理决定与相应审计。

## 7. 运行中需要处理的问题

| 场景 | 建议机制与验收重点 |
|---|---|
| 入职、调岗、离职 | 对接人员状态，检查成员／组关系和全部授权来源；调岗先明确新旧岗位的交接规则，避免只加不减 |
| 同时持有多个角色 | 展示最终有效权限及来源；撤销一个来源后检查其余来源，不能误报全部撤权成功 |
| 页面已经打开时撤权 | 后续请求重新校验，页面显示无权限状态；记录撤权确认与实际结果，不依赖菜单刷新 |
| 权限服务或授权图不可用 | 有界超时、清晰错误和恢复观测；不能绕过服务端校验。缓存如需引入，应明确陈旧上限和撤权传播，不能默认使用旧权限放行 |
| 菜单已发布，业务页面尚未部署 | 比较运行版本和路由，阻止错误入口发布或按兼容窗口控制展示 |
| 项目菜单变了但未发布 | 对比源码／运行声明和目录摘要，展示漂移状态、最后成功版本和责任方 |
| 错误发布／版本回退 | 分开处理项目回退、目录恢复、角色／授权调整；恢复展示不能视为撤销已经产生的业务效果 |
| 高权限长期累积 | 定期复核、临时授权到期及过期清理；审批、双人复核按实际风险决定，不默认加到所有操作 |

能力退役建议经过“标记弃用 → 停止新授权 → 迁移引用和有效授权 → 核验接口退出 → 退役”。这是后续设计建议，不是当前已实现状态机；历史审计和旧版本保留规则需在正式契约中确定。

目录错误的“回退”也不能直接假定重新发布较小版本即可完成：当前版本规则拒绝降低版本且要求保留旧能力。应按兼容规则发布新的修正版本；需要专门恢复操作时另行设计。

## 8. 建议建设顺序与验收方向

| 优先级 | 候选建设项 | 可观察的验收方向 |
|---|---|---|
| P0 | 菜单变更预览与授权影响分析 | 展示新增／删除／移动／路由及绑定变化；列出受影响角色版本、有效授权和去重人员，并说明统计范围和时间 |
| P0 | 发布记录与版本漂移检测 | 可关联源码提交、目录版本与摘要；漏发布和运行版本不一致能被发现 |
| P0 | 生产发布身份与目录环境隔离方案 | 未授权发布被拒绝，测试与生产不串目录；选型与契约确定后再实施 |
| P1 | 单一声明与导航可见性接入 | 项目导航和发布清单同源；用户导航按权限提示过滤，直接访问接口仍独立受控 |
| P1 | 显式角色版本迁移 | 迁移前能查看对象和差异，操作可追溯，结果可核对；旧授权不被隐式改写 |
| P1 | 权限弃用／退役治理 | 有引用检查和退出条件，删除菜单不能绕过能力退役检查 |
| P2 | 人员生命周期与周期复核 | 调岗、离职、到期后最终有效访问符合业务规则，多个来源不会遗漏 |

目前没有在本讨论中承诺容量、撤权延迟、故障恢复时间或生产可用性数字，实施时依据真实业务目标和测量范围确定。
