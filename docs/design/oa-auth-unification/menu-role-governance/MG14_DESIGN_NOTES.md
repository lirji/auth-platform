# MG14来源专项影响分析（DRAFT）

2026-10-03。MG13已交付直接来源；本文件记录MG14的已核实边界和待冻结设计，没有授予组／审批迁移执行权限，也没有修改其产品代码。

## 当前事实

- `AccessManagement.grantGroup`持久化GROUP／group_id，membership为空、generation=0，实时权限由目录组资格决定。迁移若展开成个人DIRECT，会使退组后残留权限，禁止采用。
- 当前组授权入口使用分区当前管理委派，并拒绝管理员向自己所属组授予；目录负责组、成员与任职日期。权限平台不能从任务修改组成员或重新加入离职人员。
- `AccessRequests.submit`固定角色、能力、范围、期限、策略和审批摘要；`decide`只接受可信Inbox及原固定审批人，批准与取消按分区／申请串行。OA_REQUEST来源固定为`request_id:single:request_version`，旧APPROVED并非新版批准。
- MG13的V26任务仅允许非扩权DIRECT，子项固定个人代际，来源前缀和数据库栅栏也只允许DIRECT，不能直接放开来源判断就宣称GROUP／OA已支持。

## 组来源拟采用路径

保持单个GROUP授权及原组ID，不冻结个人名单作为新授权对象。任务冻结原Grant版本、组身份、范围原字节／哈希和原截止；新来源有明确组迁移谱系，不覆盖原来源。每次效果重验当前组有效、当前管理员上限和自授限制，沿用先撤旧→确认真实回执→授新GROUP。退组人员不会被任务补回，新增组成员继续遵循原组授权的动态语义。

当前影响成员按独立诊断资格有界展示，管理权不代替诊断权。人数／来源统计不是逐资源ALLOW证明；组任务完成只报告该GROUP来源的真实投影核验，不能声称成员所有权限消失。需要追加数据库迁移、来源区分与守卫、预览／任务契约和页面，保留V26与DIRECT兼容。

## OA待决定规则

已向用户提出业务问题，尚未收到回答：

1. 推荐每次存量OA升级都重新申请审批，新批准后按原截止切换。
2. 或允许原审批负责人确认缩权迁移，扩权仍重新审批。

两种方案都必须保留旧申请／策略／批准快照，新角色与来源关系单独可追溯；普通管理者不能把OA_REQUEST转换为DIRECT，也不能伪造审批完成。新申请策略与历史申请是否可用分开处理，避免停止新申请时误改已提交审批的历史事实。

若采用重新审批，需为新申请保存原来源与目标的固定关联，批准后进入迁移检查点，再确认撤旧、创建新OA来源；不能先按原`decide`立即生成新Grant造成未决定的重叠。重试、批准／撤回、原来源外部撤权及取消新任务均按固定申请和谱系处理，不复活旧授权。此处仍为候选设计，不冻结最终HTTP／事件字段。
