# 菜单、角色与授权治理优化计划

日期：2026-10-02。状态：`APPROVED`；用户于本会话明确要求“开始实施吧”，先执行阶段 A，再按依赖推进后续阶段。

来源：[讨论归档](../MENU_ROLE_GOVERNANCE_DISCUSSION.md)。本计划是现有 OA/Auth/Commerce 改造的后续候选子计划，不改写父计划已完成状态或历史验收。唯一任务表见 [IMPLEMENTATION_SLICES.md](IMPLEMENTATION_SLICES.md)，当前状态见 [PROGRESS_STATE.md](PROGRESS_STATE.md)。

## 1. 目标和执行边界

目标是让菜单／权限变化可解释、可预览、可追溯，让项目入口与授权一致，并能受控处理角色升级、权限退役和人员变化。

规划归档阶段未修改产品。本轮已获实施授权；生产部署仍需明确目标和授权，不对已有业务角色／Grant 做未规划的改动。实施复用现有关系数据库、MyBatis XML、身份与可靠投影，不预设引入 Redis、MQ、ES 或新调度平台。计划保存与 Git 交付不代表生产部署授权。

执行建议是先完成一个可用版本：**声明同源 → 菜单差异 → 授权影响 → 受控发布 → 历史与漂移核对**。第一版沿用真实 HUMAN Owner 发布；生产自动发布和授权迁移在各自契约明确后继续。

## 5. 第一阶段具体设计方向

### 5.1 声明和身份稳定

- 首版保留现有稳定菜单编码，路由调整不重新生成身份。当前导出器通过路由构造编码且要求固定 35 页／新增 42 节点，这适合上一轮有界接入，不适合日常增删。
- 将 Commerce 导航与菜单－能力关联收敛为一个结构化声明；Auth 保存已发布快照。原权限映射中的非菜单业务规则继续由对应业务模块负责，不能强行塞进菜单配置。
- 先检查完整路由、重复菜单、父级环、未知能力和允许来源，再生成候选。保持现有最多 100 菜单／200 能力等契约上限；确需扩容另行验证。
- 新声明和项目提交关联；生成过程不登录、不写授权。原有遗留菜单的保留／移除必须显式进入差异，不以“导出成功”自动删除。

### 5.2 差异和影响

- 差异以稳定菜单编码匹配，分别比较展示、导航和权限绑定；父级的变化与继承展示影响也要报告。
- 已登记能力的资源类型／风险变更、能力删除，沿用当前拒绝规则，并清楚显示原因。API 无法从相同编码自动识别业务语义扩大，仍需能力说明与变更审查。
- “相关角色”“当前有效授权”“可能获得新入口的人”“实际对某个资源有权限的人”是不同口径。首版做潜在影响分析，不伪装成全资源实际授权证明。
- 有效统计需排除撤销／到期、停用成员和旧代际；区分 PENDING 与 ACTIVE，并结合策略／目录就绪状态。组授权需展开当前成员并去重，不能只数 Grant 行数。
- 人员／来源明细沿用独立诊断资格加当前管理委派的双重保护，限定租户／应用／环境；管理员和应用 Owner 都不能仅因管理或发布目录就读取他人授权解释。无诊断资格时明确显示不可查询，不把缺权限当零影响。首版不做无授权的跨租户全局人数。
- 服务端有界分页／聚合，不用浏览器“已加载的第一页”代替完整统计；返回统计时间、范围、完整性或需重算状态。

### 5.3 发布依据和历史

- 第一版仍使用现有真实 HUMAN Owner。新增发布记录放在独立元数据中，不给旧 manifest JSON 加字段造成历史哈希变化。
- 发布绑定候选内容哈希、展示哈希和基础目录版本；涉及人员的确认还要绑定相应影响报告依据。发布时锁定／重验；过期、基础版本变化或管理资格变化不得继续用旧确认。
- 对影响已存在人员权限语义的变更，需要业务处理决定；这不是仅凭“点击确认”证明安全。具体风险规则在 MG00／MG09 中确定。
- 目录发布仍不创建角色或 Grant。历史展示同时注明当前政策投影状态，不能把目录事务成功等同于业务鉴权已经追平。
- 漂移区分候选未发布、已发布未核验部署、部署声明不一致、核验成功和 UNKNOWN。未取得受信运行证据时不写“当前部署一致”。

## 6. 后续阶段的关键取舍

| 决策 | 建议方向 | 在哪片确定 | 尚未确定时的边界 |
|---|---|---|---|
| D-ENV：目录环境隔离 | 短期优先各环境独立实例／数据和发布目标，减少对现有应用键的迁移；确有同实例多环境需求再设计目录维度扩展 | MG09 | 阶段 A 只在明确单环境目标内运行，不开放多环境 CI 发布 |
| D-PUB：机器发布身份 | 独立受限发布权限，限定应用和部署目标；不是模拟 HUMAN Owner 或提交 operator 字段 | MG09 | 继续真实 Owner 发布；机器 Token 不自动拥有授权管理权 |
| D-NAV：业务菜单提示调用方 | 经受信 Commerce 后端复用中央用户证据与绑定；设计业务专用只读契约 | MG07 | 不把 Commerce Token 直接塞到治理管理接口，不让浏览器带服务密钥 |
| D-MIG：角色迁移连续性 | 缩权优先防止新旧权限叠加，允许短暂保守拒绝；是否要求不中断需要业务确认 | MG12 | 不迁移有效授权；不假设跨图操作原子完成 |
| D-SOURCE：迁移来源 | 首先只覆盖明确的直接授权；组授权和审批授权分别设计 | MG12、MG14 | 审批来源不能被普通管理员悄悄转成 DIRECT，新旧来源需要可追溯关联 |
| D-RET：退役语义 | 独立生命周期元数据先限制新增使用，历史角色／快照保留；最终禁止执行复用明确停用机制 | MG15 | 不通过删菜单／删历史能力“退役” |
| D-HR：岗位变更规则 | OA 保持人员事实权威；岗位角色映射、交接期和复核责任由业务确认 | MG17、MG18 | 不自动生成管理员或全员角色，不恢复已撤销来源 |

这些是建议决策，不是已批准选型。第一阶段只冻结第一阶段需要的契约，后续阶段在对应片补齐，避免先建立大量未使用抽象。

机器客户端可考虑 OAuth confidential client 的客户端凭据方式，但客户端身份认证不等于应用发布授权，必须另有受限委派和后端执行检查：[RFC 6749 §4.4](https://www.rfc-editor.org/rfc/rfc6749#section-4.4)。具体 IdP 能力和配置在 MG09 核验，不在计划中承诺当前已支持。

服务端逐请求判权、默认拒绝及授权失败处理继续遵循已有安全边界：[OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

## 7. 契约与数据库修改规则

MG00 输出本目录 `CONTRACTS.md` 的第一阶段正式内容；本轮不编造新 API JSON。MG07、MG09、MG12、MG15、MG17 按范围追加或发布相应契约版本，调用方在契约确定后实现。

每项新接口明确：谁能调用、租户／应用／环境边界、字段语义、请求上限、分页、版本检查、幂等键和作用域、错误／未知结果、兼容方式。旧预览字段和发布调用在兼容窗口保留；若新流程成为强制门禁，所有旧写入口也必须按目标应用策略执行同样检查，不能留脚本绕过路径。

按实际需要追加发布记录、受限发布委派、迁移任务／子项、能力生命周期、复核记录等持久化模型，不先一次建齐。已有最高迁移为 V20，实际实施重新核对后选下一编号，不预占 V21、不改已执行迁移。表及每个字段写中文注释，真实查询索引和唯一性约束随片验证；复杂 SQL 放在 Mapper XML。

## 8. 验收与恢复原则

- 每片带独立验证，不把新路径验收推迟到 MG19；只运行受影响单测、真实 PG 集成和必要 UI／跨进程验证。跨身份、事务、版本竞争和投影失败不能用纯 Mock 证明。
- 测试数据在获授权隔离数据库中写入，前端读真实接口。明确区分自动化契约夹具与实际身份／数据库／授权图验收。
- 页面沿用现有治理视觉和弹层组件，覆盖加载、空态、401、403、409、503、未知命令、预览失效和正常结果；1440／390／320 视口验证实际任务路径并查看截图。
- 菜单改名、删菜单、新能力未授权、新入口复用旧能力、跨环境、撤权后直接请求、多个来源、角色迁移中断、IdP／授权依赖故障都是必要场景，分别归属具体切片。
- 数据库扩展后支持旧程序继续读原快照；程序回退不撤销已发生业务效果。错误目录通过更高的新修正版本恢复兼容展示，不降低版本或删除历史。
- 迁移／退役／人员操作取消只停止未提交项；已经提交的撤权不自动恢复。恢复授权必须是新的受审计业务决定。
- 复用现有有界配置和运行组件；容量、撤权延迟、RTO/RPO 等目标按实际业务确定，未实测不编造数字。

## 9. 建议首轮范围和下一步

首轮建议执行阶段 A（MG00–MG06），完成后可以通过真实 UI 演示：“修改电商菜单 → 查看差异及受影响角色 → Owner 发布 → 查看历史／发现版本漂移”。这是一条完整发布治理路径，不自动变更原角色、Grant 或生产环境。

计划确认后的第一步是 MG00：固定第一阶段契约、统计口径和兼容边界；然后按唯一任务表串行推进。后续阶段的设计决策没有满足时只停相应依赖路径，不把第一阶段的可用交付一起阻塞。
