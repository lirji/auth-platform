## 运行范围和资源

复用现有governance-p7-rehearsal.py及Casdoor隔离/夹具工具，仅固定允许列表增加回环18094，不接受任意外部目标。默认参数仍为现有身份服务和P6/P7混部；本轮显式选择新模式，结果记录identity_mode/instance_mode，避免把混部结果误写为新版容量。

Casdoor独占本次网络，PG还保留默认bridge供既有图连接方式；这不是生产网络隔离证明。演练共用本机CPU/Docker资源，不声称完全无宿主资源竞争。JVM的-Xmx为堆上限，不是整个进程内存上限。

本轮没有应用业务源码、schema、SDK或依赖版本变化，没有接管原18090/8000身份服务、共享PG或商城。旧路径配置文件仍作为本地运行前置读取；既有工具关闭了演练实例旧图入口，不能将此理解为删除旧运行依赖配置。

## 复现和保留

在已有本地P7前置配置和当前server/admin制品基础上执行：

```bash
python3 deploy/governance-p7-rehearsal.py --isolated-identity --current-only --samples 200
```

启动资源已移到finally保护范围，失败也会停止已登记的本轮容器。正常结束停止自有JVM、代理、Casdoor、图和PG，保留网络、容器、卷、库及0600凭据/备份/日志；不删除数据。不自动停止任何原运行服务。

## 新授权就绪与中间运行

[P3既有一致性契约](../../../design/oa-auth-unification/CONTRACTS_P3_CONSISTENCY.md)允许双atLeastAsFresh水位追平前短暂保守DENY；P3-07已有新Grant追平实测。旧P7工具对新增store-mixed的首次请求立即断言ALLOW，与这个边界不符。第一轮10cbba3e6b09的三档共600容量请求均无错，但在新增授权的首次正向断言停止，不能算完整演练通过。

加上明确诊断信息后的第二轮5ba9982d05ee在同样隔离/双新版模式下23项完整检查通过，三档共600请求也无错；新Grant首次读取无需等待。这说明不能以固定睡眠或单次恰好通过代替就绪语义。

最终工具只在新授权建立后使用最多12次、间隔250ms的只读就绪探针；每次真实ALLOW/DENY/AUTHZ_STATE_NOT_READY及耗时保留。持续DENY超限失败，依赖错误/未知结果不重试。此探针不用于容量请求或撤权断言，不改生产授权判定、不将拒绝变为允许。4项独立工具测试验证上述边界，加入既有CI；第二轮及最终运行的源码指纹分别保留；第一轮仅保留检查点与样本，未生成最终结果摘要。

Code Hygiene为IMPLEMENTATION_COMPLETE_WITH_LIMITATIONS：无统一formatter、未配置独立静态分析；无阻断项。两项数字建议分别是上述固定有界探针次数/间隔及隔离身份服务子工具120秒启动截止，属于测试工具的资源边界，沿用现有脚本风格，未引入配置框架。
